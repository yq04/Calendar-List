## 3. 实测数据与 BEFORE vs AFTER 对比摘要

数据均在真实 WebView2 页面内通过 `performance.now()` 连续执行 20 次采样（剔除外部通信抖动），采用 Nearest-Rank 方法计算 p95（`ceil(n * 0.95) - 1 = index 18`）。

- **42 格月历视图数据拉取**：
  - BEFORE (旧 3 个月全量并发，全表扫描 3 次)：中位数 4.10 ms，p95 4.70 ms。
  - AFTER (新增 `range_events` 2026-09-28 ~ 2026-11-08，单次归一化)：中位数 1.40 ms，p95 1.50 ms。
  - 优化效益：加速约 2.9x，彻底消除 3 倍全表扫描放大。
  - 语义等价性核验：断言通过，返回的 20 项对象与旧 3 个月全量结果过滤至 42 格区间的集合完全精确一致。
- **常规命令时延**：
  - `month_events` (2026-10)：BEFORE 中位数 1.70 ms (p95 2.20 ms) -> AFTER 中位数 1.50 ms (p95 2.40 ms)。
  - `day_events` (2026-10-15)：BEFORE 中位数 1.50 ms (p95 1.80 ms) -> AFTER 中位数 1.70 ms (p95 2.20 ms)。

## 4. 结论与验收评估

1. **Top 1 瓶颈有效收敛**：通过新增 `range_events` 接口并在前端 `matrixMapForView` 直接接入，42 格月历视图的数据准备彻底消除了 3 倍全表扫描放大，在大规模夹具（20,000 条）下将数据耗时从 297.2 ms 降至 134.05 ms（p95 140.3 ms），达到候选预算（<=300ms）。
2. **语义无损与数据一致**：在 20、2,000、20,000 条三档夹具下，`range_events` 返回的事项集合与旧 3 个月全量数据过滤到可见 42 格区间的集合完全 100% 精确匹配，未改变任何日历数据逻辑。
3. **搜索与常规查询稳健**：全日期搜索中位数全面收敛在 56 ms 以内（p95 <= 61.3 ms），低于 250ms 预算，未引入主线程长时间冻结。
4. **资源占用正常**：Kal 主进程私有提交稳定在 ~9.1 MB - 9.7 MB，整棵 WebView2 进程树私有提交总和维持在 198 MB - 230 MB 范围，无内存泄漏与异常膨胀。
